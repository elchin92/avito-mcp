# Переход с 1.3.x на 2.0.0

**[English version →](./MIGRATION.md)** · [README](./README.ru.md) · [CHANGELOG](./CHANGELOG.md)

**Если у вас дефолтная установка по stdio — `npm install avito-mcp@2.0.0`, и на этом всё.** Ни один
инструмент не добавлен, не удалён и не переименован: те же 148 инструментов с теми же схемами, и
`schema_hash` по-прежнему `9c52d4c3…f505f`. Ни одна переменная окружения не переименована, ни один
дефолт не изменён, ни один URI ресурса и ни одно имя промпта не переехали.

Major-версию оплачивают три ужесточения в OAuth и одно изменение поведения при отмене, а не работа
над протоколом. Ревизия MCP 2026-07-28 едет выключенной.

| Ваша установка                                                      | Что делать                                                                        |
| ------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| stdio — `npx avito-mcp` в Claude Desktop, Cursor, Cline             | Ничего, если ваш клиент не отменяет вызовы. Иначе — [Отмена](#отмена-теперь-уважается) |
| HTTP с `AVITO_MCP_HTTP_AUTH=none` или `bearer`                      | Ничего                                                                            |
| HTTP с OAuth на `https://…`                                         | Прочитать [DCR стал строже](#dynamic-client-registration-стал-строже) — часть клиентов перерегистрируется |
| HTTP с OAuth на `http://…` на маршрутизируемом хосте                | **Сервер откажется стартовать.** Что делать — ниже                                |

## Единственная жёсткая поломка

2.0.0 не стартует, когда одновременно верны три вещи:

- `AVITO_MCP_TRANSPORT` равен `http` или `both`, **и**
- `AVITO_MCP_HTTP_AUTH=oauth` — это режим авторизации по умолчанию, **и**
- `AVITO_MCP_HTTP_PUBLIC_URL` — открытый `http://` на маршрутизируемом хосте:
  `http://mcp.example.com`, `http://203.0.113.5:3000`

На старте вы получите `EnvValidationError` с описанием починки. 1.3.3 стартовала спокойно, и в этом
проблема: в режиме `oauth` этот URL — сразу три вещи. Идентификатор OAuth issuer, `resource`, к
которому привязан каждый токен, и база того эндпоинта, куда клиенты POST-ят authorization code
вместе с `code_verifier`. Открытый текст выставляет наружу все три.

Дефолтную установку это не задевает: публичный URL по умолчанию — `http://127.0.0.1:3000`, loopback
исключён, а сама проверка выполняется, только когда включён HTTP-транспорт с `oauth`.

Починка — терминировать TLS на прокси и указать переменной https-адрес:

```bash
AVITO_MCP_HTTP_PUBLIC_URL=https://mcp.example.com
```

В README есть готовые [сниппеты Caddy и nginx](./README.ru.md#удалённый-mcp-по-http-oauth-21). Если
открытый HTTP действительно нужен для локальной разработки, потребуются две переменные — вторую
проверяет сам SDK, отдельно:

```bash
AVITO_MCP_HTTP_ALLOW_INSECURE_PUBLIC_URL=1
MCP_DANGEROUSLY_ALLOW_INSECURE_ISSUER_URL=true
```

На маршрутизируемом хосте так делать не надо.

## Dynamic Client Registration стал строже

Регистрация не требует авторизации, то есть адрес обратного вызова любого клиента выбирает
посторонний, а до 2.0.0 проверялись только количество (1–10) и длина. `http://evil.example.com/cb`
проходил обе проверки — и одобренный владельцем authorization code уходил по сети открытым текстом.

Теперь `redirect_uri` обязан быть `https` либо `http` на loopback-адресе (`127.0.0.1`, `[::1]`,
`localhost`) и не должен содержать фрагмент.

| Что регистрировалось раньше                    | Что делать                                            |
| ---------------------------------------------- | ------------------------------------------------------ |
| `http://` на маршрутизируемом хосте            | Перевести на `https://`                               |
| `com.example.app:/cb` (private-use схема)      | Взять loopback-редирект — поддержан с v0.9.1          |
| Любой адрес с `#fragment`                      | Убрать фрагмент                                       |

**Это наступит раньше, чем кажется.** Клиенты, уже записанные в durable-хранилище
(`AVITO_MCP_OAUTH_STORE_FILE`), при загрузке заново не проверяются и продолжают работать. Но без
этой переменной хранилище живёт в памяти — значит, при рестарте процесса перерегистрируются все, и
вот там новое правило и срабатывает. Да и «продолжают работать» не навсегда: запись клиента
истекает через 90 дней после выдачи или через 24 часа, если у неё нет живого токена или кода.

### `application_type` теперь учитывается

Клиент, объявивший `application_type: "native"`, регистрируется как публичный, с
`token_endpoint_auth_method: "none"`, и `client_secret` не получает: он едет на устройства
пользователей, а секрет, выданный такому клиенту, — это секрет, который утечёт. Заявить `native`
вместе с любым методом авторизации по секрету теперь нельзя, а клиенту `web` откажут в loopback- и
не-`https`-адресе, потому что loopback резолвится на той машине, где браузер, а не на клиенте.

Клиентов, которые `application_type` не передают, это не касается — не передавать его по-прежнему
допустимо. А вот native-клиент, который раньше получал секрет и ходил с `client_secret_post`, при
следующей регистрации упадёт, и ему придётся перейти на публичный PKCE.

## Отмена теперь уважается

Это изменение не спрятано за флагом эры. Оно действует на обеих ревизиях, включая дефолтную, и это
единственное наблюдаемое изменение поведения для дефолтной stdio-установки.

1.3.3 разбирала `notifications/cancelled` и ничего с этим не делала. 2.0.0 на него реагирует:
обработчик, превращающий уведомление в `abort()`, регистрируется базовым протоколом SDK ещё до
того, как ревизия известна, а слой инструментов читает сигнал отмены, не сверяясь с эрой. Ревизия
2026-07-28 добавляет второй канал — закрытие потока ответа, — но первым не владеет. Если ваш клиент
уведомление не шлёт, ничего из этого вас не касается.

Если шлёт — нового будет два. Вызов, от которого клиент ушёл, теперь прерывается, а не доходит до
конца. И если прерывание застало **опасный инструмент с `idempotencyKey`, чей запрос уже был
отправлен в Avito**, исход отсюда неизвестен: мутация могла пройти. Ключ переводится в ограниченное
по времени удержание, и повтор с ним отвечает `IDEMPOTENCY_HELD` вместо исполнения.

Этот отказ и есть смысл. Для денежной операции «нет» лучше второго списания. Отмена *до* отправки
запроса — пока он стоял в очереди за бюджетом лимитера или ждал токен — освобождает ключ ровно как
раньше, а слот ограничителя частоты возвращается в любом случае.

Флага, возвращающего поведение 1.3.3, нет: он вернул бы вместе с собой и двойное списание. Если
наткнулись на удержанный ключ, в `docs/safety.md` есть раздел
[Lifting a held idempotency key](./docs/safety.md) — удержание истекает само по TTL реестра, либо
вы удаляете файл записи, названный в `warn`-строке, после сверки с аккаунтом.

## Что вы, скорее всего, не заметите

**В npm-тарболе стало меньше файлов.** Поле `files` сузило `docs/` до `docs/safety.md`, поэтому ADR
и `docs/conformance.md` больше не попадают в опубликованный пакет. В рантайме их никто не читает —
`avito://docs/safety` единственный документ, который сервер отдаёт. Читайте их в репозитории.

**Подменён фундамент зависимостей.** `@modelcontextprotocol/sdk ^1.29` ушёл в пользу
`@modelcontextprotocol/{server,server-legacy,node,express} ^2.0.0`, а HTTP-слоем современного
транспорта стал `hono ^4.12`. У пакета нет карты `exports` и потребляют его через `bin`, так что
поломки публичного API нет — но если вы импортируете пути `dist/*` напрямую или держите старый SDK
как peer, вас это касается. `engines` (`node >=22.12.0`), `bin` и `main` не менялись.

**Исправлен баг 1.3.3:** `tools/call` без члена `arguments` теперь проходит. 1.3.3 отвергала такой
запрос для любого инструмента, включая те, что аргументов не принимают вовсе, — например
`meta_capabilities`, — хотя в спецификации член необязательный. Это строго послабление: то, что
работало раньше, сломаться не может.

## По желанию: включить ревизию MCP 2026-07-28

Пока переменная не выставлена, ничего не меняется. По умолчанию она выключена.

| `AVITO_MCP_PROTOCOL_ERA` | Что обслуживает процесс                                                           |
| ------------------------ | ---------------------------------------------------------------------------------- |
| `legacy` *(по умолчанию)* | Только ревизию 2025-11-25 — побайтово провод 1.3.x                               |
| `dual`                   | Обе. Клиент 2025 зовёт `initialize`, клиент 2026 — `server/discover`               |
| `modern`                 | Только 2026-07-28, а значит бросает всех клиентов 2025 года                        |

Выкатывайте через `dual`, посмотрите, потом сужайте. Нераспознанное значение роняет старт, а не
откатывается к дефолту: опечатка в единственной переменной, решающей, какой протокол получат ваши
клиенты, не должна переживаться молча. Что увидит клиент, перешедший на 2026-07-28, — в README, в
разделе [Ревизии протокола](./README.ru.md#ревизии-протокола).

**Одно ограничение, о котором стоит знать до включения `dual`.** На stdio эра выбирается один раз
за соединение и потом не меняется. Слоя заголовков там нет, поэтому SDK читает ревизию из первого
классифицируемого сообщения и держит её до конца соединения. Клиент 2026 года, у которого в первом
кадре нет конверта `_meta`, будет обслужен как клиент 2025 года до переподключения, даже если
конверт есть во всех последующих кадрах. Сервер в этот момент пишет в stderr одну строку
`protocol era pinned to legacy` с именем метода, который закрепил эру, — её и грепайте при выкате.
Чинится на стороне клиента: слать `io.modelcontextprotocol/protocolVersion` в `params._meta` уже в
первом сообщении. HTTP это не задевает: там каждый запрос классифицируется сам по себе. Почему это
принято, а не обойдено: [ADR 0001](./docs/adr/0001-protocol-era-limitations.md).

**Два новых лимита вместо ограничений на сессии.** У ревизии 2026-07-28 сессий нет, поэтому
`AVITO_MCP_HTTP_MAX_SESSIONS` и `AVITO_MCP_HTTP_SESSION_IDLE_SEC` — они сохранили имена, дефолты и
смысл — на современной ноге ничем не управляют. Эквивалентный бюджет там несут две новые переменные:

```bash
AVITO_MCP_HTTP_MAX_INFLIGHT=64   # одновременных обменов на /mcp
AVITO_MCP_HTTP_MAX_STREAMS=32    # сколько из них могут быть долгими потоками
```

Они намеренно не выводятся из `maxSessions`: сессия большую часть жизни простаивает, а обмен в
полёте — это работа, и связывание сдвигало бы современный бюджет каждый раз, когда оператор
подкручивает legacy. Обе видны в `avito://state/config`.

## Откат

```bash
npm install avito-mcp@1.3.3
```

Ничего предварительно отменять не нужно. 2.0.0 не пишет новых форматов на диск: runtime-state, кеш
токена и файл OAuth-хранилища — те же, что у 1.3.3. Единственное добавление — поле `issuer`,
которое хранилище OAuth заводит при первой записи под 2.0.0, а 1.3.3 читает только известные ей
поля, поэтому откат поверх безопасен.

Если нужно откатить только новую ревизию протокола, а остальное оставить, снимите
`AVITO_MCP_PROTOCOL_ERA` (или поставьте `legacy`) и перезапустите. Это полный откат работы над
ревизией, без переустановки.

## Вопросы

**Изменился ли хоть один инструмент?** Нет — 148 инструментов, те же имена, те же входные схемы, тот
же `schema_hash`. Набор тестов сверяет эту сборку с эталоном провода, снятым с настоящего
работающего процесса 1.3.3: 61 записанный обмен, 151 утверждение, на каждом прогоне CI.

**Обязательно ли включать 2026-07-28?** Нет. По умолчанию выключено и инертно, пока не задана
переменная.

**Заметит ли что-нибудь мой агент?** Только если он отменяет вызовы инструментов.

**Сломалось что-то ещё.** Заведите [issue](https://github.com/elchin92/avito-mcp/issues) со
значениями `AVITO_MCP_TRANSPORT`, `AVITO_MCP_HTTP_AUTH` и `AVITO_MCP_PROTOCOL_ERA` — но никогда не
с доступами — и выводом `meta_health`.

Подробности, включая всё, что не попало сюда: [CHANGELOG 2.0.0](./CHANGELOG.md).
