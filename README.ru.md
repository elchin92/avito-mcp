**MCP-сервер, который передаёт ваш аккаунт на Avito AI-агенту — чтобы вы перестали его открывать.**
Агент отвечает покупателям в чатах, держит объявления в цене и в продвижении, ведёт заказы через
доставку, передаёт коды маркировки и приносит вам цифры. Не один раз, для демонстрации: по
расписанию или в момент, когда клиент написал. 148 инструментов по 18 официальным API Avito — это
средство. Ставят его ради того, что ежедневные полчаса кликов перестают быть вашими.

Трудная часть обещания — слово «без вас», поэтому большая часть сервера сделана именно для того,
чтобы агента можно было оставить наедине с боевым аккаунтом. Потратить деньги стоит двух вызовов,
а не одного. Попросите опасный инструмент прогнать вхолостую — он напечатает точный HTTP-запрос
вместо того, чтобы его отправить. А повтор с тем же ключом идемпотентности вернёт первый результат.

## Быстрый старт

Node.js 22.12 или новее. Без клонирования, без сборки, без Docker.

**1.** Возьмите `Client_id`, `Client_secret` и числовой `Profile_id` в
[кабинете разработчика Avito](https://www.avito.ru/professionals/api). Все три — на одной странице.

**2.** Положите это в конфиг вашего MCP-клиента. JSON одинаковый для всех клиентов — отличается
только путь к файлу, и они собраны в разделе [Подключение AI-клиента](#подключение-ai-клиента).

```json
{
  "mcpServers": {
    "avito": {
      "command": "npx",
      "args": ["-y", "avito-mcp"],
      "env": {
        "Client_id": "YOUR_CLIENT_ID",
        "Client_secret": "YOUR_CLIENT_SECRET",
        "Profile_id": "YOUR_PROFILE_ID"
      }
    }
  }
}
```

**3.** Перезапустите клиент и спросите: _«Какой у меня баланс на Авито и сколько непрочитанных чатов?»_

Два вызова API, настоящий ответ, и доступы не покидали машину — stdio стоит транспортом по
умолчанию, и ничего не проксируется через чужой сервер.

## Что агент реально умеет

Каждый публичный endpoint из 18 OpenAPI-спецификаций Avito — это инструмент, сгенерированный из
приложенных swagger-файлов, а не написанный руками: покрытие определяет API, а не чей-то вкус.

| Группа                    | Штук | Для чего это агенту                                                          |
| ------------------------- | ---: | ----------------------------------------------------------------------------- |
| Мессенджер                |   16 | Читать чаты, отвечать, слать картинки, блокировать, подписываться на события |
| Объявления                |   11 | Цены, просмотры/контакты/звонки, аналитика, расходы, платные услуги          |
| Заказы                    |   12 | Статусы, слоты курьера, трек-номера, этикетки, «Честный знак»                |
| Автозагрузка              |   17 | Выгрузка XML/YML/CSV, отчёты по позициям, маппинг ID, схемы категорий        |
| Продвижение и CPA         |   25 | Прогнозы и заказы BBIP, ставки CPA, аукционы, жалобы, баланс                 |
| Доставка (партнёрский 3PL) |  31 | Логистический API Avito для служб доставки — продавцу почти никогда не нужен |
| Профиль, остатки, штат    |   14 | Баланс, история операций, остатки, суб-аккаунты, отзывы и ответы на них      |
| Тарифы, trxpromo, звонки  |   12 | Справочник тарифов, транзакционное продвижение, записи звонков, скидки       |
| Auth и meta               |   10 | Здоровье, capabilities, лимиты, поток подтверждений, сырые OAuth-токены      |

Снимок API Avito в `./swaggers/` — от 25 мая 2026 года. Avito меняет методы без предупреждения;
404 на документированном методе или отсутствующий новый — повод завести issue, и снимок обновят.
Живой каталог с риском, доменом и аннотациями по каждому инструменту — это ресурс
`avito://manifest` или `dist/manifest.json` после сборки: он генерируется, а не лежит в репозитории.

**Сколько инструментов вы увидите на самом деле** — зависит от конфигурации. Четыре из 148
включаются явно: три возвращают OAuth-токены, один читает картинки с вашего диска.

| Конфигурация                                                       | Зарегистрировано |
| ------------------------------------------------------------------ | ---------------: |
| По умолчанию (`AVITO_MCP_MODE=full_access`, ничего не включено)    |              144 |
| `+ AVITO_MCP_ALLOWED_UPLOAD_DIRS=…` (загрузка изображений)         |              145 |
| `+ AVITO_MCP_EXPOSE_AUTH_TOOLS=1` (три инструмента `auth_*`)       |              147 |
| Оба opt-in — полный манифест                                       |              148 |
| `AVITO_MCP_MODE=guarded` (прячет риски `money` и `public`)         |              119 |
| `AVITO_MCP_MODE=read_only` (только `risk=read`)                    |               80 |
| `AVITO_MCP_CONFIRMATION_MODE=off`                                  |     −3 meta-тула |

Скрытые инструменты не регистрируются вовсе, поэтому их нет и в `tools/list` — модель не может
вызвать то, чего не видит. `AVITO_MCP_ALLOW_TOOLS` и `AVITO_MCP_DENY_TOOLS` сужают набор поимённо
для роя агентов, где агенту поддержки незачем держать в руках бюджет на продвижение.

## Почему его можно оставить работать

У каждого инструмента один из пяти классов риска, и класс решает, что произойдёт до отправки
вызова: `read` 80, `write` 40, `public` 16, `money` 9, `sensitive` 3. Классы видны клиенту как
MCP `ToolAnnotations` и `_meta.risk`, так что оркестратор может маршрутизировать по ним.

**Деньги и публичные действия требуют второго вызова.** По умолчанию (`money_public`) всё, что
тратит деньги или видно покупателю, возвращает `{ requires_confirmation: true, confirmation_id: … }`
вместо исполнения. Агент — или человек, читающий у него через плечо — вызывает
`meta_confirm_action` с этим идентификатором. Pending-состояние durable, привязано к аккаунту,
одноразовое и живёт 15 минут; `all_destructive` распространяет барьер на любую запись.
`AVITO_MCP_CONFIRMATION_SECRET` делает барьер жёстким, а `AVITO_MCP_APPROVAL_MODE=external`
дополнительно требует, чтобы подтверждающий отличался от того, кто действие начал.
[`docs/safety.md`](./docs/safety.md) честно говорит, что это такое: серверный two-step и слой
аудита, а не криптографическое доказательство, что подтвердил человек.

**Любое опасное действие можно прогнать вхолостую.** Передайте `dryRun: true` — и инструмент вернёт
HTTP-запрос, который он бы сделал: метод, путь, тело; `fetch` не вызывается. Переверните дефолт на
весь процесс через `AVITO_MCP_DRY_RUN_DEFAULT=true` или `--dry-run`, и тогда агенту придётся
осознанно передать `dryRun: false`, чтобы действовать.

```json
{ "name": "items_update_price", "arguments": { "item_id": 12345, "price": 1400, "dryRun": true } }
```

**Повтор — не второе списание.** Любой опасный инструмент принимает `idempotencyKey`. Резервация
пишется в durable-реестр, привязанный к аккаунту, до мутации на стороне Avito, поэтому повтор с тем
же ключом и теми же аргументами отдаёт закешированный результат (`idempotent_replay: true`) без
второго HTTP-вызова, а тот же ключ с другими аргументами — структурированную ошибку конфликта.
Реестр переживает рестарт и общий для параллельных stdio-процессов. Брошенная резервация закрывается
наглухо и просит сверки вместо того, чтобы предположить, что возможно оплаченное действие безопасно
повторить. TTL — `AVITO_MCP_IDEMPOTENCY_TTL_SEC` (час), хранилище — `AVITO_MCP_RUNTIME_STATE_DIR`.

**Ошибки машинно-читаемы**, чтобы агент ветвился по полям, а не по английскому тексту:

```json
{ "isError": true, "structuredContent": { "error": {
  "type": "AVITO_RATE_LIMIT", "message": "Avito API 429 for POST …",
  "retryable": true, "retryAfter": 60, "httpStatus": 429 } } }
```

`type` — одно из `AVITO_BAD_REQUEST`, `AVITO_UNAUTHORIZED`, `AVITO_FORBIDDEN`, `AVITO_NOT_FOUND`,
`AVITO_RATE_LIMIT`, `AVITO_SERVER_ERROR`, `AVITO_API_ERROR`, `NETWORK_ERROR`, `TIMEOUT`,
`CONFIG_ERROR`, `INTERNAL_ERROR`, `IDEMPOTENCY_HELD`. Успешные ответы тоже несут `structuredContent`:
объекты как `{ status, …data, http_status }`, массивы как `{ status, http_status, items, count }`,
бинарники (PDF-этикетки, аудио звонков) как `{ status, http_status, mimeType, sizeBytes, base64 }`.

**Три meta-инструмента описывают сервер сам себе** — `meta_health` (версия, аптайм, счётчики),
`meta_auth_status` (только метаданные токена, никогда сам токен, `probe: true` пробует обновить) и
`meta_capabilities` (активный режим, размеры allow/deny, флаги возможностей). У всех трёх строгие
выходные схемы. `meta_get_rate_limits` показывает `X-RateLimit-*` Avito по доменам, а сами лимиты
общие на весь процесс, а не считаются отдельно в каждом месте вызова.

**Несколько процессов делят один токен.** Если cron, чат-сессия и CLI работают с одним token-файлом,
они не ломятся в `/token` Avito одновременно: первый берёт `{tokenFile}.lock` и обновляет токен,
остальные ждут и читают свежий с диска. Аренда проверяет владельца, поэтому lock мёртвого процесса
переиспользуется, а живого — не крадётся (`AVITO_MCP_TOKEN_LOCK_TIMEOUT_MS`, 30 с).

Насколько это всё проверено: 915 тестов в 54 файлах, 84% операторов и 87% строк покрытия, включая
151 утверждение, которое сверяет эту сборку с эталоном провода, снятым с настоящего работающего
процесса 1.3.3 — так что рефакторинг не изменит тихо то, что получает существующий клиент.

## Ресурсы и промпты

Ресурсы — это данные, которые агент читает, не тратя вызов к API Avito. На два из них можно
подписаться, и именно это делает возможным цикл без присмотра.

| URI                             | Что внутри                                                               |
| ------------------------------- | ------------------------------------------------------------------------ |
| `avito://docs/safety`           | Режимы безопасности, поток подтверждений, готовые конфигурации           |
| `avito://manifest`              | Живой каталог инструментов — риск, домен, заголовок, аннотации           |
| `avito://state/config`          | Снимок активной конфигурации, секреты вырезаны                           |
| `avito://state/rate-limits`     | Последние `X-RateLimit-*` по каждому домену Avito                        |
| `avito://state/pending-actions` | Подтверждения, которые кого-то ждут — **подписываемый**                  |
| `avito://webhook/events`        | Буфер событий чатов Avito — **подписываемый**                            |
| `avito://swaggers/{slug}`       | По ресурсу на каждую приложенную спецификацию, с автодополнением         |

Промпты — готовые сценарии, которые зовут нужные инструменты в нужном порядке, причём ограничители
записаны прямо в текст промпта, а не оставлены на усмотрение модели.

| Промпт                     | Аргументы             | Что делает                                                      |
| -------------------------- | --------------------- | ---------------------------------------------------------------- |
| `avito_daily_overview`     | `days?` (по ум. 7)    | Баланс, активные объявления, расходы — только чтение            |
| `avito_check_unread_chats` | `limit?` (по ум. 20)  | Разбор непрочитанных чатов с явным запретом отправлять          |
| `avito_promote_item`       | `item_id`             | Всё нужное перед платной покупкой VAS — и без самой покупки     |
| `avito_explain_tool`       | `tool_name`           | Запись инструмента в манифесте вместе с его swagger-описанием   |
| `avito_safety_report`      | —                     | Сервер описывает вам собственную посадку                        |

Отдельные события сервера — смена режима, отчёт о скрытых инструментах, жизненный цикл
подтверждений, предупреждения о лимитах — уходят клиенту как `notifications/message` с вырезанными
чувствительными полями. Логирование pino в stderr при этом не меняется.

## Удалённый MCP по HTTP (OAuth 2.1)

stdio стоит по умолчанию и это правильный ответ для одного человека за одним ноутбуком. Когда один
аккаунт нужен нескольким клиентам, хостовому агенту или телефону, те же 148 инструментов отдаются
по Streamable HTTP за OAuth 2.1 — authorization code с PKCE, динамическая регистрация клиентов и
экран согласия, который человеку придётся пройти.

```bash
AVITO_MCP_TRANSPORT=http                            # stdio (по умолчанию) | http | both
AVITO_MCP_HTTP_PUBLIC_URL=https://mcp.example.com   # ваш TLS-домен, без слэша на конце
AVITO_MCP_OAUTH_OWNER_PASSWORD=…                    # обязателен, случайный, минимум 32 байта
# Client_id / Client_secret / Profile_id как обычно — аккаунт, от имени которого работает сервер
```

Клиент находит authorization server по 401 на `/mcp`, регистрируется на `/register` и открывает
`/authorize` в браузере. Пароль владельца, введённый на этой странице, — единственное, что выпускает
токен; эндпоинт ограничен по частоте, чтобы его не подобрали. Токены привязаны к точному scope
`avito:mcp` и точному resource URL этой установки, а каждая сессия — к principal, который её открыл.
`both` поднимает stdio и HTTP в одном процессе.

| Эндпоинт                                    | Что это                                                        |
| ------------------------------------------- | ---------------------------------------------------------------- |
| `/mcp`                                      | Собственно MCP-транспорт                                        |
| `/authorize`                                | Экран согласия — сюда вводится пароль владельца                 |
| `/token` · `/register` · `/revoke`          | Обмен кода, динамическая регистрация (RFC 7591), отзыв          |
| `/.well-known/oauth-authorization-server`   | Метаданные authorization server                                 |
| `/.well-known/oauth-protected-resource/mcp` | Метаданные ресурса, path-suffixed по RFC 9728                   |
| `/healthz` · `/readyz`                      | Liveness и readiness, без авторизации, тела вида `{ok}`         |

| Переменная                                 | По умолчанию | Смысл                                                                                                         |
| ------------------------------------------ | ----------- | ---------------------------------------------------------------------------------------------------------------- |
| `AVITO_MCP_TRANSPORT`                      | `stdio`     | `stdio` \| `http` \| `both` (CLI: `--http`, `--both`)                                                          |
| `AVITO_MCP_HTTP_HOST` / `_PORT`            | `127.0.0.1` / `3000` | Адрес и порт. Держите loopback, а наружу пусть смотрит прокси                                         |
| `AVITO_MCP_HTTP_PUBLIC_URL`                | —           | Идентификатор OAuth issuer. Его смена — это другой authorization server: клиенты перерегистрируются, токены гаснут |
| `AVITO_MCP_HTTP_AUTH`                      | `oauth`     | `oauth` \| `bearer` \| `none`                                                                                  |
| `AVITO_MCP_OAUTH_OWNER_PASSWORD`           | —           | Обязателен в режиме `oauth`, минимум 32 байта. Единственный секрет, выпускающий токен                          |
| `AVITO_MCP_OAUTH_TOKEN_TTL_SEC`            | `3600`      | Время жизни выпущенного bearer-токена                                                                          |
| `AVITO_MCP_OAUTH_STORE_FILE`               | —           | Durable-хранилище клиентов и токенов. Эксклюзивная аренда — один сервер на файл                                |
| `AVITO_MCP_HTTP_AUTH_TOKEN`                | —           | Режим `bearer`: общие секреты через запятую, каждый минимум 32 байта                                           |
| `AVITO_MCP_HTTP_ALLOWED_HOSTS` / `_ORIGINS` | derived    | Защита от DNS-rebinding. Выводится fail-closed; неполный wildcard-bind не даст стартовать                       |
| `AVITO_MCP_HTTP_ALLOW_INSECURE_PUBLIC_URL` | `0`         | Только для разработки. Открытый issuer на маршрутизируемом хосте; SDK ещё требует `MCP_DANGEROUSLY_ALLOW_INSECURE_ISSUER_URL` |
| `AVITO_MCP_HTTP_ALLOW_NO_AUTH`             | `0`         | Разрешить `auth=none` вне loopback. Не рекомендуется, и это ровно то, чем звучит                               |
| `AVITO_MCP_HTTP_MAX_SESSIONS`              | `100`       | **Только ревизия legacy** (сессии есть у 2025-11-25). Одновременных сессий; сверх — `initialize` получит 503   |
| `AVITO_MCP_HTTP_SESSION_IDLE_SEC`          | `1800`      | **Только ревизия legacy.** Простаивающие дольше сессии закрываются — клиент ушёл, не прислав `DELETE`          |
| `AVITO_MCP_HTTP_MAX_INFLIGHT`              | `64`        | Ревизия 2026-07-28, где сессий нет: одновременных обменов на `/mcp` до `503` + `Retry-After`                   |
| `AVITO_MCP_HTTP_MAX_STREAMS`               | `32`        | Сколько из них могут быть долгими потоками подписок, чтобы потоки не вытесняли обычные вызовы                  |

Node слушает loopback и говорит открытым HTTP; TLS — работа обратного прокси. Никогда не выставляйте
порт 3000 наружу. Сохраняйте заголовок `Host` — метаданные OAuth строятся из него.

<details>
<summary>Сниппеты Caddy и nginx для <code>https://mcp.example.com</code></summary>

```caddyfile
mcp.example.com {
    # Caddy сам получает сертификаты и по умолчанию сохраняет Host.
    reverse_proxy /mcp* /authorize* /token* /register* /revoke* /healthz* /readyz* \
                  /.well-known/oauth-* /avito/webhook* http://127.0.0.1:3000
}
```

```nginx
server {
    listen 443 ssl;
    server_name mcp.example.com;
    ssl_certificate     /etc/letsencrypt/live/mcp.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/mcp.example.com/privkey.pem;

    location ~ ^/(mcp|\.well-known/oauth-|authorize|token|register|revoke|avito/webhook|healthz|readyz) {
        proxy_pass         http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header   Host $host;             # из этого строятся метаданные OAuth
        proxy_set_header   X-Forwarded-Proto $scheme;
        proxy_buffering    off;                    # Streamable HTTP держит ответы открытыми
        proxy_read_timeout 3600s;
    }
}
```

</details>

Если вы владеете обоими концами и полный поток избыточен, работает `AVITO_MCP_HTTP_AUTH=bearer` с
общим секретом. Скажем прямо, чем за это платят: **режимы `bearer` и `none` не заявляют соответствия
авторизационной части спецификации MCP.** Ни один не публикует метаданные защищённого ресурса, ни
один не поднимает authorization server, а 401 — это голый `Bearer realm="avito-mcp"`: MCP-клиент не
сможет узнать, где авторизоваться, и не пройдёт поток, который обязан начать сам. Для MCP-клиентов
берите `oauth`; `bearer` — для вызывающего, которого вы настраиваете руками.

## Приёмник webhook Avito

Опрос новых чатов работает, но агенту, который отвечает за секунды, события нужно доставлять. В
сервере есть приёмник: отдаёте Avito секретный URL, и каждое событие буферизуется для агента. Это
работает и в чистом stdio-режиме — Avito нужен лишь публичный URL для POST, а ваш MCP-клиент его
вообще не касается. Если при `AVITO_MCP_TRANSPORT=stdio` задан секрет вебхука, поднимается
маленький HTTP-listener ровно под приёмник.

```bash
AVITO_MCP_WEBHOOK_SECRET=…                            # случайный, минимум 32 байта
AVITO_MCP_WEBHOOK_PUBLIC_URL=https://mcp.example.com  # по умолчанию берётся публичный HTTP URL
# AVITO_MCP_WEBHOOK_PATH=/avito/webhook               # AVITO_MCP_WEBHOOK_BUFFER=100
# AVITO_MCP_WEBHOOK_LOG_FILE=/var/lib/avito-mcp/webhook-events.jsonl
```

Avito доставляет на `{PUBLIC_URL}{PATH}/{SECRET}` и получает `200 {"ok":true}` заметно раньше
двухсекундного дедлайна Avito. Секрет — сегмент пути, и в этом вся авторизация: URL неугадываем,
он обязан быть публичным HTTPS, а 32 случайных байта — нижняя граница. Оба инструмента регистрации
принимают только тот URL приёмника, который следует из конфигурации оператора, поэтому агент не
перенаправит будущие сообщения куда захочет, а в dry-run секрет вырезается.

События читаются через `messenger_get_webhook_events` (фильтры `chat_id`, `since`, `limit`) или
подпиской на `avito://webhook/events` с уведомлением в момент доставки. Что лежит в буфере, скажет
`messenger_get_webhook_status`. Необязательный лог-файл — `0600`, только нормализованные метаданные,
без текста сообщений и сырого payload, ротация на 10 MiB и один бэкап.

## Эксплуатация

```bash
avito-mcp --readonly        # AVITO_MCP_MODE=read_only          --guarded
avito-mcp --dry-run         # AVITO_MCP_DRY_RUN_DEFAULT=true    --no-confirmation
avito-mcp --http | --both   # AVITO_MCP_TRANSPORT=http | both
avito-mcp --health          # напечатать JSON-снимок здоровья и выйти
avito-mcp --version | --help
```

Флаги — сахар над переменными окружения, и переменная побеждает, если заданы обе. Всё остальное —
переменные окружения; их перечисляет `--help`, и они же в [.env.example](./.env.example).

`--health` — диагностика конфигурации, а не liveness-проба: он не разговаривает с уже запущенным
процессом. Для Kubernetes или супервизора используйте `/readyz` — он отвечает 200, только пока
слушатель открыт, доступы для HTTP-режима заполнены целиком, каталоги токена и runtime-state
доступны на запись, аренда OAuth-хранилища жива, а запись вебхуков не падала. Тело остаётся `{"ok":…}`.

Разбор переменных окружения намеренно fail-fast: неизвестное значение enum, наполовину числовой
лимит, слабый удалённый секрет или число вне диапазона останавливают старт, а не откатываются к
дефолту, который вы не выбирали. Узнать об этом на старте лучше, чем из счёта.

## Протокол и совместимость

Этот раздел можно пропустить, если к вашей установке не подключаются посторонние. Дефолтная
установка отвечает той же ревизией, что и раньше, и ничего здесь не меняется без вашей переменной.

### Ревизии протокола

`AVITO_MCP_PROTOCOL_ERA` выбирает, какие ревизии MCP обслуживает процесс: `legacy` (по умолчанию —
только 2025-11-25, побайтово провод 1.3.x), `dual` (обе), `modern` (только 2026-07-28).
Нераспознанное значение роняет старт, а не откатывается к дефолту: опечатка в переменной, которая
решает, какой протокол получат ваши клиенты, не должна переживаться молча.

|                              | 2025-11-25                                | 2026-07-28                                                        |
| ---------------------------- | ----------------------------------------- | ------------------------------------------------------------------- |
| Рукопожатие                  | `initialize`                              | нет — `server/discover` и пер-запросный конверт `_meta`             |
| Слежение за ресурсом         | `resources/subscribe`                     | `subscriptions/listen` с `resourceSubscriptions` и подтверждением   |
| Подписываемые URI            | pending-действия, события вебхука         | те же два                                                           |
| `listChanged`                | объявлен `true`                           | объявлен `false` — что для этого сервера и есть правда              |
| Списочные запросы            | один ответ (≈225 КБ), `cursor` игнорируется | страницы по 48 КиБ; невыданный курсор — `-32602`                  |
| Аргументы промптов           | любая строка, `parseInt(…) \|\| default`  | allowlist, границы у чисел, отказ на управляющие и bidi-символы     |
| Уровень логов                | `logging/setLevel` на соединение          | этот метод removed; уровень объявляется на запрос в `_meta`         |
| Отмена вызова                | `notifications/cancelled`                 | то же, либо закрытие потока ответа                                  |

Разница по `listChanged` сделана осознанно. Наборы инструментов, промптов и ресурсов у этого сервера
фиксированы на всю жизнь процесса, поэтому уведомление `list_changed` не уходит никогда. На
2025-11-25 объявленное `true` инертно и оставлено ради совместимости провода. На 2026-07-28 оно не
инертно: `subscriptions/listen` сужает фильтр клиента ровно по этим битам, так что `true` подтвердило
бы подписку на уведомления, которых не будет, и клиент ждал бы их вместо опроса.

Схемы инструментов отдаются в диалекте JSON Schema draft-07 на обеих ревизиях. 2026-07-28 разрешает
2020-12, но не требует, оба диалекта дают для этого каталога идентичные тела, а
`meta_capabilities.schemaHash` считается по схемам в том виде, в каком они уходят, — так что смена
диалекта сломала бы всех, кто следит за этим хэшем. Ни одна схема не ссылается на сетевой URI.

> **На stdio ревизия выбирается один раз за соединение.** Слоя заголовков там нет, поэтому SDK
> читает её из первого классифицируемого сообщения и держит до конца соединения. При `dual` клиент
> 2026 года, у которого в первом кадре нет конверта `_meta`, будет обслужен как клиент 2025 года
> до переподключения, даже если конверт есть во всех последующих кадрах. В этот момент сервер
> пишет в stderr одну строку `protocol era pinned to legacy` с именем метода, который эру закрепил,
> — её и грепайте при выкате. Чинится на стороне клиента: слать
> `io.modelcontextprotocol/protocolVersion` в `params._meta` уже в первом сообщении. HTTP это не
> задевает, там каждый запрос классифицируется сам по себе. Почему мы это принимаем, а не форкаем
> входную точку SDK: [ADR 0001](docs/adr/0001-protocol-era-limitations.md).

> **Отмена уважается на обеих ревизиях, а 1.3.3 не уважала её ни на одной.** Эта строка таблицы —
> единственная, где колонки описывают одно поведение, а не различие: abort ставит базовый протокол
> SDK ещё до того, как ревизия известна. Отмена прерывает исходящий вызов к Avito и возвращает слот
> ограничителя частоты; аренда идемпотентности освобождается, только если запрос ещё не был
> отправлен. Отмена, догнавшая уже отправленный запрос, переводит ключ в ограниченное удержание, и
> следующий вызов с ним отвечает `IDEMPOTENCY_HELD` — см.
> [ADR 0008](docs/adr/0008-idempotency-hold-on-cancelled-dispatch.md). Для денежной операции отказ
> лучше вероятного двойного списания.

### Версионирование

Публичная поверхность живёт по [SemVer](https://semver.org) с версии 1.0.0. Стабильно, то есть
поломка стоит major: имена инструментов и все документированные Avito-валидные формы входа, имена и
дефолты переменных окружения, URI ресурсов `avito://`, имена промптов, модель рисков, таксономия
ошибок, флаги CLI. Аддитивно, то есть minor: новые инструменты вслед за новыми методами Avito, новые
opt-in переменные, новые ресурсы и промпты. Приложенный снимок swagger — данные, а не API: его
обновление стоит minor, пока существующие имена инструментов продолжают работать.

Одно честное исключение. Исправление контракта или безопасности не обещает и дальше принимать вход,
который приложенная спецификация Avito уже отвергает: minor или security-релиз может добавить
конечную анти-абузную границу, поднять недооценённый риск операции, ограничить операторский адрес
утечки или выкинуть EOL-линию Node.js. Такое ужесточение обязано сохранить документированные
Avito-валидные вызовы, кроме случая, когда именно это поведение и есть уязвимость, и каждый такой
случай требует явных указаний по переходу в changelog. Всё прочее по-прежнему стоит major.

Переход с 1.3.x — [MIGRATION.ru.md](./MIGRATION.ru.md); коротко: дефолтной stdio-установке не нужно
ничего, а одна HTTP-конфигурация откажется стартовать.

## Безопасность

- stdio по умолчанию: без прокси, без удалённых эндпоинтов, без телеметрии. HTTP-режим включается
  явно, слушает loopback и закрыт OAuth 2.1 или bearer-секретом за вашим собственным TLS.
- Доступы живут в блоке `env` клиента или в локальном `.env` и не уходят никуда, кроме
  `api.avito.ru`. OAuth-токены кешируются по аккаунту в файле `0600` внутри каталога `0700` —
  `$XDG_STATE_HOME/avito-mcp/token.json` на Linux, `~/Library/Application Support/avito-mcp/` на
  macOS, `%APPDATA%\avito-mcp\` на Windows или там, куда указывает `AVITO_TOKEN_FILE`. Кеш, созданный
  для другого origin, клиента или профиля, игнорируется. Удалите файл, чтобы принудительно обновить.
- `messenger_upload_images` читает файлы с диска, поэтому без `AVITO_MCP_ALLOWED_UPLOAD_DIRS` он
  вообще не регистрируется. С ним инструмент проверяет ровно тот дескриптор, который открыл,
  отбивает гонки по родительскому и финальному симлинку, держит лимиты числа и объёма, сверяет
  magic-байты jpg/jpeg/png/webp и не пускает локальные пути в текст ошибок.
- Три инструмента `auth_*` возвращают OAuth-токены. Они помечены `sensitive` и скрыты даже в
  `full_access`, пока не выставлен `AVITO_MCP_EXPOSE_AUTH_TOOLS=1`.
- Считайте боевым каждый инструмент с `environment: prod`, потому что он боевой: sandbox-доступов
  Avito не выдаёт, и любой вызов из этого пакета идёт в живой аккаунт. Операции доставки, которые
  Avito документирует как sandbox, помечены `environment: sandbox` — это метаданные, а не защита.
  Безопасные первые вызовы: `user_get_user_balance`, `items_get_items_info`, `messenger_get_chats_v2`.
- Обновляете боевую установку? [`docs/adr/0002-canary-protocol.md`](./docs/adr/0002-canary-protocol.md)
  — это пять read-only инструментов, которые прогоняются на реальном аккаунте после рискованного
  выката при выставленном `AVITO_MCP_MODE=read_only`. В [`docs/safety.md`](./docs/safety.md) лежат
  готовые конфигурации: только аналитика, поддержка клиентов, только объявления, полный админ.
- Нашли уязвимость? Приватный канал описан в [SECURITY.md](./SECURITY.md). Пожалуйста, не заводите
  под это публичный issue.

## Установка из исходников

Для разработки, изолированных установок или когда нужно поменять инструмент. Node.js `>=22.12.0`;
CI гоняет набор тестов на 22.x и 24.x.

```bash
git clone https://github.com/elchin92/avito-mcp.git && cd avito-mcp
npm ci && cp .env.example .env      # затем впишите три доступа
npm run build:release               # собирает код и перегенерирует dist/manifest.json
```

Укажите клиенту `{ "command": "node", "args": ["/absolute/path/to/dist/server.js"] }`. В комплекте
есть многоступенчатый [`Dockerfile`](./Dockerfile).

Для укреплённого развёртывания через systemd: напишите `.remote.env`, выполните
`npm run verify:release`, затем `sudo deploy/install-services.sh --start`. Инсталлятор переносит
только переменные avito-mcp в root-owned `/etc/avito-mcp/avito-mcp.env`, создаёт read-only релиз в
`/opt/avito-mcp/releases/<version>`, атомарно переключает симлинк `current`, запускает процесс от
непривилегированного пользователя и проверяет `/readyz` вместе с версией, которую отдаёт
`/healthz`. Выкаты сериализуются через `flock`, а любая ошибка возвращает прежний симлинк, конфиг,
юниты и состояние процессов. Пересборка изменённого кода под тем же номером версии намеренно ничего
не делает — сначала поднимите версию.

Добавить новый API Avito — это один файл в `src/domains/` и одна строка в
`src/meta/domain-registry.ts`; фабрика в `src/core/tool-factory.ts` уже берёт на себя HTTP, OAuth,
ретраи, учёт лимитов, отображение ошибок и подстановку `Profile_id`, так что ни один инструмент не
пишет `fetch()`. Подробности — в [CONTRIBUTING.md](./CONTRIBUTING.md).
