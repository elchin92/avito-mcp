## Ресурсы и промпты

Ресурсы предоставляют локальные данные сервера без вызова API Avito. На два из них можно подписаться; внешний агент может использовать уведомления как вход для сценария обработки событий.

| URI                             | Что внутри                                                       |
| ------------------------------- | ---------------------------------------------------------------- |
| `avito://docs/safety`           | Режимы безопасности, поток подтверждений, готовые конфигурации   |
| `avito://manifest`              | Живой каталог инструментов — риск, домен, заголовок, аннотации   |
| `avito://state/config`          | Снимок активной конфигурации, секреты вырезаны                   |
| `avito://state/rate-limits`     | Последние `X-RateLimit-*` по каждому домену Avito                |
| `avito://state/pending-actions` | Действия, ожидающие подтверждения — **подписываемый**            |
| `avito://webhook/events`        | Буфер событий чатов Avito — **подписываемый**                    |
| `avito://swaggers/{slug}`       | По ресурсу на каждую приложенную спецификацию, с автодополнением |

Промпты содержат инструкции для сценария. MCP-клиент читает их и выбирает вызовы инструментов; получение промпта само по себе не выполняет сценарий.

| Промпт                     | Аргументы                 | Что делает                                                     |
| -------------------------- | ------------------------- | -------------------------------------------------------------- |
| `avito_daily_overview`     | `days?` (1–270; по ум. 7) | Баланс, активные объявления, расходы — только чтение           |
| `avito_check_unread_chats` | `limit?` (по ум. 20)      | Разбор непрочитанных чатов с явным запретом отправлять         |
| `avito_promote_item`       | `item_id`                 | Проверка объявления и условий платного продвижения без покупки |
| `avito_explain_tool`       | `tool_name`               | Запись инструмента в манифесте вместе с его swagger-описанием  |
| `avito_safety_report`      | —                         | Текущие режимы и ограничения сервера                           |

Отдельные события сервера — смена режима, отчёт о скрытых инструментах, жизненный цикл
подтверждений, предупреждения о лимитах — уходят клиенту как `notifications/message` с вырезанными
чувствительными полями. Логирование pino в stderr при этом не меняется.

## Удалённый MCP по HTTP (OAuth 2.1)

stdio используется по умолчанию для локального клиента. Для удалённого агента или нескольких клиентов используйте Streamable HTTP. OAuth поддерживает authorization code с PKCE, динамическую регистрацию и страницу подтверждения владельцем.

```bash
AVITO_MCP_TRANSPORT=http                            # stdio (по умолчанию) | http | both
AVITO_MCP_HTTP_PUBLIC_URL=https://mcp.example.com   # ваш TLS-домен, сохраняйте этот issuer URL неизменным
AVITO_MCP_OAUTH_OWNER_PASSWORD=…                    # обязателен, случайный, минимум 32 байта
# Client_id / Client_secret / Profile_id как обычно — аккаунт, от имени которого работает сервер
```

Клиент находит authorization server по 401 на `/mcp`, регистрируется на `/register` и открывает
`/authorize` в браузере. Для подтверждения нужен пароль владельца; число попыток ограничено. Затем клиент обменивает код авторизации на токен и может обновлять его в пределах срока действия. Токены привязаны к точному scope
`avito:mcp` и точному resource URL этой установки, а legacy-сессия — к principal, который её открыл. Современные запросы авторизуются независимо.
`both` поднимает stdio и HTTP в одном процессе.

| Эндпоинт                                    | Что это                                                 |
| ------------------------------------------- | ------------------------------------------------------- |
| `/mcp`                                      | Собственно MCP-транспорт                                |
| `/authorize`                                | Экран согласия — сюда вводится пароль владельца         |
| `/token` · `/register` · `/revoke`          | Обмен кода, динамическая регистрация (RFC 7591), отзыв  |
| `/.well-known/oauth-authorization-server`   | Метаданные authorization server                         |
| `/.well-known/oauth-protected-resource/mcp` | Метаданные ресурса, path-suffixed по RFC 9728           |
| `/healthz` · `/readyz`                      | Liveness и readiness, без авторизации, тела вида `{ok}` |

| Переменная                                  | По умолчанию         | Смысл                                                                                                                         |
| ------------------------------------------- | -------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `AVITO_MCP_TRANSPORT`                       | `stdio`              | `stdio` \| `http` \| `both` (CLI: `--http`, `--both`)                                                                         |
| `AVITO_MCP_HTTP_HOST` / `_PORT`             | `127.0.0.1` / `3000` | Адрес и порт локального слушателя; публичный доступ через TLS-прокси                                                          |
| `AVITO_MCP_HTTP_PUBLIC_URL`                 | —                    | Идентификатор OAuth issuer. Его смена — это другой authorization server: клиенты перерегистрируются, токены гаснут            |
| `AVITO_MCP_HTTP_AUTH`                       | `oauth`              | `oauth` \| `bearer` \| `none`                                                                                                 |
| `AVITO_MCP_OAUTH_OWNER_PASSWORD`            | —                    | Обязателен в режиме `oauth`, минимум 32 байта. Защищает подтверждение на странице владельца                                   |
| `AVITO_MCP_OAUTH_TOKEN_TTL_SEC`             | `3600`               | Время жизни выпущенного bearer-токена                                                                                         |
| `AVITO_MCP_OAUTH_STORE_FILE`                | —                    | Постоянное хранилище клиентов и токенов; один работающий сервер на файл                                                       |
| `AVITO_MCP_HTTP_AUTH_TOKEN`                 | —                    | Режим `bearer`: общие секреты через запятую, каждый минимум 32 байта                                                          |
| `AVITO_MCP_HTTP_ALLOWED_HOSTS` / `_ORIGINS` | derived              | Защита от DNS-rebinding. Проверка допустимых хостов и Origin; недостаточная конфигурация останавливает запуск                 |
| `AVITO_MCP_HTTP_ALLOW_INSECURE_PUBLIC_URL`  | `0`                  | Только для разработки. Открытый issuer на маршрутизируемом хосте; SDK ещё требует `MCP_DANGEROUSLY_ALLOW_INSECURE_ISSUER_URL` |
| `AVITO_MCP_HTTP_ALLOW_NO_AUTH`              | `0`                  | Разрешить `auth=none` вне loopback. Отключает защиту удалённого доступа                                                       |
| `AVITO_MCP_HTTP_MAX_SESSIONS`               | `100`                | **Только ревизия legacy** (сессии есть у 2025-11-25). Одновременных сессий; сверх — `initialize` получит 503                  |
| `AVITO_MCP_HTTP_SESSION_IDLE_SEC`           | `1800`               | **Только ревизия legacy.** Простаивающие дольше сессии закрываются — клиент ушёл, не прислав `DELETE`                         |
| `AVITO_MCP_HTTP_MAX_INFLIGHT`               | `64`                 | Ревизия 2026-07-28, где сессий нет: одновременных обменов на `/mcp` до `503` + `Retry-After`                                  |
| `AVITO_MCP_HTTP_MAX_STREAMS`                | `32`                 | Сколько из них могут быть долгими потоками подписок, чтобы потоки не вытесняли обычные вызовы                                 |

Node слушает loopback и говорит открытым HTTP; TLS — работа обратного прокси. Никогда не выставляйте
порт 3000 наружу. Сохраняйте публичные host и scheme; адрес issuer задаётся в `AVITO_MCP_HTTP_PUBLIC_URL`.

<details>
<summary>Сниппеты Caddy и nginx для <code>https://mcp.example.com</code></summary>

```caddyfile
mcp.example.com {
    # Caddy сам получает сертификаты и по умолчанию сохраняет Host.
    reverse_proxy 127.0.0.1:3000
}
```

```nginx
server {
    listen 443 ssl;
    server_name mcp.example.com;
    ssl_certificate     /etc/letsencrypt/live/mcp.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/mcp.example.com/privkey.pem;

    location ~ ^/(mcp|\.well-known/oauth-|authorize|token|register|revoke|avito/webhook|healthz|readyz) {
        proxy_pass         http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header   Host $host;             # сохраняем публичный host
        proxy_set_header   X-Forwarded-Proto $scheme;
        proxy_buffering    off;                    # Streamable HTTP держит ответы открытыми
        proxy_read_timeout 3600s;
    }
}
```

</details>

`AVITO_MCP_HTTP_AUTH=bearer` подходит для клиента, которому общий секрет задан вручную. Режимы `bearer` и `none` не реализуют OAuth discovery: в них нет authorization server и метаданных защищённого ресурса. Используйте `oauth`, если клиент должен самостоятельно найти сервер авторизации и пройти его поток.

## Приёмник webhook Avito

Не допускайте попадания секретного URL в журналы прокси. [Пример Caddy](../deploy/Caddyfile.example) исключает webhook из access-лога, но error-лог может содержать путь при недоступном upstream. Проверяйте оба журнала и ограничивайте доступ к ним.

Необязательный приёмник сохраняет входящие события в буфер. Для доставки Avito нужен публичный HTTPS URL. Приёмник может работать вместе со stdio: запускается отдельный HTTP-слушатель для webhook, без публикации MCP по HTTP.

```bash
AVITO_MCP_WEBHOOK_SECRET=…                            # случайный, минимум 32 байта
AVITO_MCP_WEBHOOK_PUBLIC_URL=https://mcp.example.com  # по умолчанию берётся публичный HTTP URL
# AVITO_MCP_WEBHOOK_PATH=/avito/webhook               # AVITO_MCP_WEBHOOK_BUFFER=100
# AVITO_MCP_WEBHOOK_LOG_FILE=/var/lib/avito-mcp/webhook-events.jsonl
```

Avito отправляет события на `{PUBLIC_URL}{PATH}/{SECRET}`; успешная доставка получает `200 {"ok":true}`. Секрет в пути служит фактором авторизации, поэтому URL должен быть HTTPS, а секрет — случайным и длиной не менее 32 байт. Инструменты регистрации принимают только URL из конфигурации оператора. Предпросмотр скрывает секрет.

События читаются через `messenger_get_webhook_events` (фильтры `chat_id`, `since`, `limit`) или
подпиской на `avito://webhook/events` с уведомлением в момент доставки. Что лежит в буфере, скажет
`messenger_get_webhook_status`. Необязательный лог-файл — `0600`, только нормализованные метаданные,
без текста сообщений и сырого payload, ротация на 10 MiB и один бэкап.

## Эксплуатация

```bash
avito-mcp --readonly        # AVITO_MCP_MODE=read_only          --guarded
avito-mcp --dry-run         # AVITO_MCP_DRY_RUN_DEFAULT=true    --no-confirmation
avito-mcp --http           # AVITO_MCP_TRANSPORT=http; --both enables both transports
avito-mcp --health          # напечатать JSON-снимок здоровья и выйти
avito-mcp --version
avito-mcp --help
```

Флаги задают значения по умолчанию для переменных окружения; явно заданная переменная имеет приоритет. Всё остальное —
переменные окружения; их перечисляет `--help`, и они же в [.env.example](../.env.example).

`--health` — диагностика конфигурации, а не liveness-проба: он не разговаривает с уже запущенным
процессом. Для Kubernetes или супервизора используйте `/readyz` — он отвечает 200, только пока
слушатель открыт, доступы для HTTP-режима заполнены целиком, каталоги токена и runtime-state
доступны на запись, аренда OAuth-хранилища жива, а запись вебхуков не падала. Тело остаётся `{"ok":…}`.

Разбор переменных окружения намеренно fail-fast: неизвестное значение enum, наполовину числовой
лимит, слабый удалённый секрет или число вне диапазона останавливают старт, а не откатываются к
дефолту, который вы не выбирали. Исправьте указанное значение перед повторным запуском.

## Развёртывание через systemd

На Linux-хосте с systemd подготовьте `.remote.env` с HTTP-настройками и доступами Avito, выполните `npm run verify:release`, затем `sudo deploy/install-services.sh --start` из каталога исходников. Перед запуском прочитайте [установщик](../deploy/install-services.sh) и [переменные окружения](../.env.example).

Установщик создаёт ограниченную сервисную учётную запись, `/etc/avito-mcp/avito-mcp.env` с владельцем root и релиз в `/opt/avito-mcp/releases/<version>`. Ссылка `current` переключается атомарно; затем проверяются готовность и версия. Развёртывания сериализованы через `flock`; при ошибке восстанавливаются прежние релиз, конфигурация и состояние сервиса. Изменённый код под прежней версией не считается новым релизом: перед таким обновлением увеличьте версию.

## Протокол и совместимость

В 2.1.1 сохраняется встроенный OAuth-сервер с [переходной SDK-зависимостью](adr/0004-own-authorization-server.md). Внешний провайдер идентификации не требуется; текущие регистрации, токены и экран подтверждения продолжают работать.

Версия 2.1.0 намеренно исправляет промпт отчёта и обработку неизвестного результата в обеих ревизиях; см. [CHANGELOG](../CHANGELOG.md). Это уточняет обещание совместимости миграции 2.0.0.

Далее — справка для операторов и разработчиков клиентов. Ревизия по умолчанию в 2.1.1 остаётся legacy.

### Ревизии протокола

`AVITO_MCP_PROTOCOL_ERA` выбирает, какие ревизии MCP обслуживает процесс: `legacy` (по умолчанию —
только 2025-11-25, поверхность протокола 1.3.x с исправлениями 2.1.0), `dual` (обе), `modern` (только 2026-07-28).
Нераспознанное значение роняет старт, а не откатывается к дефолту: опечатка в переменной, которая
решает, какой протокол получат ваши клиенты, не должна переживаться молча.

|                      | 2025-11-25                                         | 2026-07-28                                                        |
| -------------------- | -------------------------------------------------- | ----------------------------------------------------------------- |
| Рукопожатие          | `initialize`                                       | нет — `server/discover` и пер-запросный конверт `_meta`           |
| Слежение за ресурсом | `resources/subscribe`                              | `subscriptions/listen` с `resourceSubscriptions` и подтверждением |
| Подписываемые URI    | pending-действия, события вебхука                  | те же два                                                         |
| `listChanged`        | объявлен `true`                                    | объявлен `false` — что для этого сервера и есть правда            |
| Списочные запросы    | один ответ (≈225 КБ), `cursor` игнорируется        | страницы по 48 КиБ; невыданный курсор — `-32602`                  |
| Аргументы промптов   | прежняя валидация; период daily overview ограничен | allowlist, границы у чисел, отказ на управляющие и bidi-символы   |
| Уровень логов        | `logging/setLevel` на соединение                   | этот метод removed; уровень объявляется на запрос в `_meta`       |
| Отмена вызова        | `notifications/cancelled`                          | то же, либо закрытие потока ответа                                |

Разница по `listChanged` сделана осознанно. Наборы инструментов, промптов и ресурсов у этого сервера
фиксированы на всю жизнь процесса, поэтому уведомление `list_changed` не уходит никогда. На
2025-11-25 объявленное `true` инертно и оставлено ради совместимости провода. На 2026-07-28 оно не
инертно: `subscriptions/listen` сужает фильтр клиента ровно по этим битам, так что `true` подтвердило
бы подписку на уведомления, которых не будет, и клиент ждал бы их вместо опроса.

Схемы инструментов отдаются в диалекте JSON Schema draft-07 на обеих ревизиях. 2026-07-28 разрешает
2020-12, но не требует, оба диалекта дают для этого каталога идентичные тела, а
`meta_capabilities.schemaHash` считается по схемам в том виде, в каком они уходят, — так что смена
диалекта сломала бы всех, кто следит за этим хэшем. Ни одна схема не ссылается на сетевой URI.

> **На stdio ревизия выбирается один раз за соединение.** Слоя заголовков там нет, поэтому SDK
> читает её из первого классифицируемого сообщения и держит до конца соединения. При `dual` клиент
> 2026 года, у которого в первом кадре нет конверта `_meta`, будет обслужен как клиент 2025 года
> до переподключения, даже если конверт есть во всех последующих кадрах. В этот момент сервер
> пишет в stderr одну строку `protocol era pinned to legacy` с именем метода, который эру закрепил,
> — проверяйте эту запись при развёртывании. Исправление на стороне клиента: отправлять
> `io.modelcontextprotocol/protocolVersion` в `params._meta` уже в первом сообщении. Для HTTP это ограничение не действует: каждый запрос классифицируется отдельно. Обоснование: [ADR 0001](../docs/adr/0001-protocol-era-limitations.md).

> **Отмена действует на обеих ревизиях.** До отправки запроса ключ освобождается; после отправки действует блокировка отмены с TTL. Потеря ответа с неизвестным результатом использует бессрочную блокировку. См. [восстановление](safety.md#lost-responses-after-a-mutation-v21).

### Версионирование

Проект использует [SemVer](https://semver.org). Имена инструментов, документированные допустимые аргументы, переменные окружения и их значения по умолчанию, URI ресурсов, промпты, модель рисков, ошибки и CLI относятся к публичному контракту.

| Изменение                                                | Тип выпуска |
| -------------------------------------------------------- | ----------- |
| Несовместимый публичный контракт                         | Major       |
| Новые инструменты, opt-in настройки, ресурсы или промпты | Minor       |
| Совместимые исправления и документация                   | Patch       |

Исправления безопасности и соответствия API могут ужесточать недопустимые аргументы, ограничения злоупотреблений, классификацию риска или небезопасные настройки. Документированные допустимые вызовы сохраняются, кроме случая, когда само поведение является уязвимостью. Для каждого такого изменения нужны описание и указания по переходу. Прекращение поддержки устаревшей версии Node.js также описывается явно.

Изменения для установленной версии перечислены в [руководстве по обновлению](../MIGRATION.ru.md).
