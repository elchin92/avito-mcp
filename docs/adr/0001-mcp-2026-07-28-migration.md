# ADR 0001. Миграция avito-mcp на ревизию MCP 2026-07-28

- **Статус:** принят. Задача плана M0.1; раздел «Предусловия» закрывает M0.2.
- **Дата:** 2026-08-01
- **Базовое состояние:** ветка `main`, коммит `6d4c7a5`, avito-mcp **1.3.3**, `@modelcontextprotocol/sdk@^1.30.0`.
- **Оговорка к замерам.** Предполётные измерения П1–П9 сделаны 2026-07-31…2026-08-01 на коммите `79ed1cb` при `@modelcontextprotocol/sdk@1.29.0`. Последующий бамп 1.29.0 → 1.30.0 схемы не сдвинул: `dist/manifest.json` побайтово идентичен, `schema_hash` прежний. Значения `npm ls` перепроверены на текущем `main` и приведены ниже уже в актуальном виде.

## Соглашение о ссылках на источники

Ссылки вида `versioning.md:143-144`, `sdk-typescript-5.md:97` и подобные указывают на **внутренний исследовательский корпус** `docs/mcp-2026-07-28/` — 66 файлов (65 тематических + `00-INDEX.md`, ~8,4 МБ) с выгрузкой спецификации 2026-07-28, changelog'ов, SEP и документации SDK.

Корпус намеренно **не хранится в этом репозитории**: он внесён в `.gitignore`, исключён из npm-пакета и из Docker-образа и покрыт гейтом в `test/release-hardening.test.ts` (задача M0.5, закрыта в PR #43). Он существует только в рабочем чекауте сопровождающего.

Поэтому такие ссылки оформлены **обычным кодом, а не гиперссылками**: для стороннего читателя они не битые ссылки, а указатели на внутренний материал, который в публичный артефакт сознательно не входит. То же относится к `MIGRATION_PLAN.md` и `MIGRATION_PROGRESS.md` — они тоже untracked по решению В2. Всё, что нужно для понимания и проверки решений, процитировано в тексте настоящего ADR дословно, так что читать корпус для оценки решений не требуется.

## Контекст

Ревизия MCP **2026-07-28** ломает базовые предположения avito-mcp: удалён `initialize` и протокольные сессии, введён `server/discover` и per-request `_meta`-конверт, `resources/subscribe` заменён на `subscriptions/listen`, все результаты обязаны нести `resultType`, а фича Logging депрекирована. Одновременно официальный TypeScript SDK разъехался на две линии: замороженную `@modelcontextprotocol/sdk@1.x` и новую `@modelcontextprotocol/{core,server,client,…}@2.x`.

Этот ADR фиксирует восемь решений, которые иначе будут переприниматься на каждом PR, и четыре процедурных решения владельца проекта. Он не описывает _как_ мигрировать — это `MIGRATION_PLAN.md`; он описывает, _что и почему решено раз и навсегда_.

Состояние на момент замера:

**Поправка к аудиту, зафиксированная письменно:** утверждение «в `package.json` нет полей `files` и `exports`» верно только наполовину. `exports`, `publishConfig`, `overrides` действительно отсутствуют, а `files` **есть** и содержит запись `docs/` — весь каталог целиком, без исключений. Корпус попадал в пакет **не из-за отсутствия allowlist, а из-за слишком широкой записи `docs/` в уже существовавшем allowlist** при отсутствующем `.npmignore`. Это меняет и формулировку причины, и форму лечения: чинится сужением записи, а не введением нового механизма.

**Состояние после PR #43 (M0.5 закрыта):** `files` перечисляет `docs/safety.md` пофайлово, каталог `docs/mcp-2026-07-28/` внесён в `.gitignore` и `.dockerignore`, `Dockerfile` копирует `docs/safety.md`, а не `docs/`, гейт в `test/release-hardening.test.ts` падает при любой попытке расширить `docs/`-запись обратно до каталога. Тарбол вернулся к базовой линии: **127 файлов, 480 kB сжатого, 2,7 MB распакованного** (было 193 / 2,8 MB / 11,4 MB).

**Следствие для настоящего ADR.** Поскольку allowlist теперь перечисляет под `docs/` ровно один файл, каталог `docs/adr/` (включая этот документ и ADR 0002) в npm-тарбол **не попадает** — он живёт в git и на GitHub, но не в пакете. Это осознанно: ADR — проектная документация для контрибьюторов, а не часть поставки. Гейт `release-hardening` дополнительно требует, чтобы любое будущее расширение набора `docs/`-файлов в пакете делалось явным решением.

Измерение сделано с `--ignore-scripts`, поэтому использован уже лежащий на диске `dist/`. Реальный `npm pack`/`npm publish` сначала выполнит `prepack` → `build:release`, поэтому число файлов `dist/` может незначительно отличаться; к 66 корпусным файлам это не относится.

## Решения

### Решение 1. Целевое состояние — dual-era-сервер, а не modern-only

**Решение.** avito-mcp обслуживает обе эры одновременно, на одном эндпоинте и в одном процессе. Modern-only не является целью этой миграции; условия и процедура возможного перехода к нему вынесены в задачу M8.5 и требуют отдельного решения.

**Обоснование.** Спецификация прямо разрешает эту конфигурацию, и только она не имеет ни одной ячейки `Fails` в матрице совместимости. Modern-only-сервер ломает legacy-клиента без возможности отката с его стороны, а подавляющее большинство установленных MCP-клиентов на момент выхода ревизии ещё legacy. Правила эры разведены по тому, как клиент открывает диалог, поэтому dual-era не требует эвристик: modern-запрос несёт per-request `_meta`, legacy-клиент шлёт `initialize`.

**Источник.**

- `versioning.md:143-144` — «A dual-era server **MAY** serve both eras concurrently on the same endpoint or process.»
- `versioning.md:457` — матрица: Modern-сервер + Legacy-клиент — «Fails. The server may reject the request with an implementation-defined error, stay silent, or even process an era-ambiguous method under legacy semantics.»
- `versioning.md:458-461` — Dual-era + Modern «Works», Dual-era + Legacy «Works», Legacy-клиент + Dual-era «Works».
- `versioning.md:790` — «A request carrying modern per-request `_meta` is served statelessly according to this revision. An `initialize` request selects legacy semantics, scoped to the stdio process (stdio) or the session (HTTP), as specified by the negotiated legacy protocol version.»
- `versioning.md:242` — требование `405` на GET/DELETE квалифицировано словами «supports only this revision», то есть на dual-era-сервер в таком виде не распространяется.
- `versioning.md:815` — пока мы dual-era, `supportedVersions` в `server/discover` должен честно перечислять обе эры.

**Подтверждение реализуемости (П1).** SDK поддерживает это нативно: `ALL_CODECS = [rev2025Codec, rev2026Codec]`, публичный тип `ProtocolEra = 'legacy' | 'modern'`, у `serveStdio` опция `legacy?: 'serve' | 'reject'` («the same factory serves both eras»), у `createMcpHandler` — `legacy?: 'stateless' | 'reject'` плюс `isLegacyRequest()` для внешней маршрутизации.

**Следствия.** Wire-снапшот legacy-пути (M1.1) становится обязательным гейтом на весь срок миграции. Списки версий двух эр в SDK разделены намеренно — «so adding a revision here can never leak a modern version string into a 2025-era handshake», — и наш код обязан это разделение сохранять, а не сводить в один список.

### Решение 2. Переезд на пакеты v2 и принятие ревизии — два раздельных релиза

**Решение.** Сначала релиз, который меняет только поверхность SDK (v1 → v2) и **не меняет ни одного байта на проводе**; затем, отдельными релизами, — принятие ревизии 2026-07-28 за feature-флагом. Смешивать это в одном релизе запрещено.

**Обоснование.** Это не организационное удобство, а свойство самого SDK: v2 по умолчанию не говорит на 2026-07-28, вход в новую эру — всегда явный opt-in через отдельные точки входа. Значит переезд поверхности объективно проверяем снапшотом провода (ничего не должно измениться), а принятие ревизии меняет всё и требует другого метода проверки. Смешанный релиз лишает нас единственного дешёвого критерия корректности первого шага.

**Источник.**

- `sdk-typescript-5.md:97` — «Nothing in v2 puts a 2026-07-28 byte on the wire by default: a hand-constructed `Client` / `Server` / `McpServer` keeps speaking the 2025-era protocol it was written for. Serving or speaking 2026-07-28 is always an explicit opt-in via one of the entries below.»
- `sdk-typescript-5.md:89` — «The codemod handles the v1→v2 SDK surface upgrade only — adopting the 2026-07-28 protocol revision (`createMcpHandler`, multi-round-trip requests, `versionNegotiation`) is architectural and not codemod-automatable»
- `sdk-typescript-5.md:15` — вывод корпуса: «обновление до 2026-07-28 — это не bump версии зависимости, а два последовательных проекта».
- `sdk-typescript-5.md:1154` — «stdio: заменить `server.connect(new StdioServerTransport())` на `serveStdio(() => buildServer())`».

**Подтверждение фактами (П1, П2, П9).** Линия v2 существует, стабильна и реализует ревизию; линия v1 её не реализует и не будет. Поэтому решение остаётся в силе и **не является блокером**. Дополнительное подтверждение того, что это именно два проекта: кодмод закрывает почти весь механический слой (30 файлов, после него 0 ошибок typecheck по `src/`), но не трогает ни `createMcpHandler`, ни `serveStdio` — после его прогона `src/http/mcp-http.ts` по-прежнему руками управляет сессиями, а `src/server.ts` по-прежнему делает `new StdioServerTransport()` + `server.connect(transport)`.

**Поправка 2a: публичной константы `"2026-07-28"` в v2 нет.** `LATEST_PROTOCOL_VERSION` в `@modelcontextprotocol/core@2.0.0` по-прежнему равен `"2025-11-25"` — это legacy-константа для `initialize`. `MODERN_WIRE_REVISION` помечен «Internal only — deliberately NOT a public constant (G-D2-4: no public modern-version constant ships before era-aware list semantics exist)». Поэтому эра **определяется не сравнением с импортированной константой**, а через публичный тип `ProtocolEra` (`'legacy' | 'modern'`), классификацию входящего запроса средствами SDK и ответ `server/discover`. Везде, где код, план или обсуждение предполагают импорт публичной константы ревизии из `core`, формулировку надо переписать на этот способ определения эры.

**Поправка 2b: modern-эра по stdio недостижима без `serveStdio(factory)`.** Ручная конструкция `new StdioServerTransport()` + `server.connect(transport)` остаётся **legacy-эрой навсегда** — «hand-constructed instances and unclassified traffic are legacy-era» (DV-13, default posture). Отдавать 2026-07-28 по stdio можно только через `serveStdio(factory, options)`, которая «owns the era decision for the connection» и обслуживает обе эры из одной фабрики (`legacy?: 'serve' | 'reject'`). Практическое следствие: после механического переезда на v2 (M2.6 меняет только импорт `StdioServerTransport` на подпуть `@modelcontextprotocol/server/stdio`) stdio остаётся строго legacy — это **ожидаемое состояние, а не регрессия**; собственно вход в modern-эру по stdio делает задача M3.2.

### Решение 3. `confirmation_id` остаётся основным механизмом подтверждения; MRTR — опциональная надстройка

**Решение.** Двухходовка `confirmation_id` + `meta_confirm_action` сохраняется как единственный обязательный путь подтверждения money/public-операций. `InputRequiredResult` (MRTR) в этом цикле не внедряется; его оценка как _дополнительного_ пути вынесена в M8.1.

**Обоснование.** Ревизия удаляет протокольные сессии и предписывает серверам, которым нужно состояние между вызовами, использовать явные server-minted handles, передаваемые обычными аргументами инструментов. Наш `confirmation_id` — ровно этот механизм, причём durable, кросс-процессный и с атомарным claim: он переживает stateless без единой правки. MRTR же протаскивает `requestState` через клиента, то есть через недоверенную сторону; для денежных операций это строго слабее. Спецификация делает MRTR разрешением (**MAY**), а не обязанностью, и жёстко ограничивает его тремя методами.

**Источник.**

- `seps-1.md:1064` / `server-tools.md:1209` (SEP-2567) — «Remove protocol-level sessions and the `Mcp-Session-Id` header from the Streamable HTTP transport. … Servers that need cross-call state use explicit, server-minted handles passed as ordinary tool arguments.»
- `seps-1.md:1004` — «This proposal removes the protocol-level session concept from MCP, replacing implicit session-scoped state with explicit, server-minted state handles that the model carries and threads through subsequent calls.»
- `server-tools.md:140-141` — «Servers **MAY** respond to `tools/call` with an `InputRequiredResult` to indicate that additional input is needed before the tool call can be completed.» — уровень MAY.
- `spec-core.md:1160` — «Servers **MUST NOT** send `InputRequiredResult` responses on any other client requests.» (разрешены только `prompts/get`, `resources/read`, `tools/call`).
- `spec-core.md:954` — оценка корпуса: «собственный двухшаговый flow концептуально совпадает с MRTR … **Если** когда-нибудь переводить подтверждения на MRTR, надо будет выполнить требования N10–N13: `requestState` считать вводом от атакующего, защищать HMAC/AEAD, класть внутрь принципала, TTL и идентификатор исходного запроса, а для одноразовых действий обеспечивать single-use на сервере.»
- `deprecated.md` — elicitation в реестре Deprecated **отсутствует**, то есть отказ от MRTR не является ставкой на депрекированную фичу.

**Следствия.** Если MRTR когда-либо будет добавлен (M8.1), он добавляется как _второй_ путь при сохранении первого, и обязан выполнить N10–N13 целиком. Существующие заготовки — `AVITO_MCP_CONFIRMATION_SECRET` и durable idempotency.

### Решение 4. Расширение `io.modelcontextprotocol/tasks` в этом цикле не внедряется

**Решение.** Расширение MCP Tasks не реализуется. Проверяемый инвариант: при пустом окружении ответ `server/discover` не содержит непустого поля `extensions`. Оценка целесообразности вынесена в M8.2.

**Обоснование.** Расширения по определению выключены по умолчанию и требуют явного opt-in с **обеих** сторон; сервер, не реализующий ни одного расширения, полностью соответствует протоколу. То есть отказ не создаёт ни одного невыполненного нормативного требования. При этом Tasks — недавно переработанное расширение, вынесенное из ядра, нормативный текст которого живёт в отдельном репозитории и в корпус не входит; строить на нём money-операции без прочитанной нормативной спецификации нельзя.

**Источник.**

- `extensions-1.md:81-82` — «Extensions are always disabled by default and require explicit opt-in from the developer.»
- `extensions-1.md:129-130` — «Extensions are always opt-in: a client only uses an extension if both client and server declare support in the `extensions` field of their capabilities.»
- `extensions-1.md:139-140` — «Task support requires explicit opt-in from both client and server.»
- `extensions-1.md:951` — «Базовый вывод: никаких обязательных действий этот раздел не создаёт. Расширения опциональны, всегда выключены по умолчанию … сервер, не реализующий ни одного расширения, полностью соответствует протоколу.»
- `extensions-1.md:544` (changelog, SEP-2663) — «Move experimental tasks out of the core protocol and into an official extension (`io.modelcontextprotocol/tasks`). The redesigned extension replaces the blocking `tasks/result` method with polling via `tasks/get` …»
- `extensions-1.md:354` — полная спецификация лежит в `experimental-ext-tasks` и в корпус не загружалась; там же зафиксировано расхождение в названии репозитория (`experimental-ext-tasks` против `ext-tasks`).

**Следствия.** Любое расширение, если оно когда-либо появится, включается отдельной переменной `AVITO_MCP_*` со значением по умолчанию «выключено» — так же, как остальная конфигурация проекта (`extensions-1.md:957`).

### Решение 5. Аннотация `x-mcp-header` не используется

**Решение.** Ни одна схема инструмента avito-mcp не несёт `x-mcp-header`. Решение закрепляется автоматическим гардом (M5.8) и фиксируется в `docs/safety.md` (M7.2).

**Обоснование.** Три независимые причины. Первая — у нас нет сценария: механизм нужен, когда перед сервером стоит посредник, маршрутизирующий по значению параметра инструмента; у avito-mcp такого посредника нет. Вторая — безопасность: сервер проксирует запросы в живой боевой Avito API, и любая возможность клиента влиять на исходящие заголовки — новая поверхность атаки; спецификация отдельно предупреждает не помечать так чувствительные параметры. Третья — цена ошибки асимметрична: одно невалидное значение обязывает клиента выкинуть **весь инструмент** из `tools/list`, то есть опечатка молча уменьшает набор инструментов у пользователя.

**Источник.**

- `server-tools.md:120-121` — «Server developers **SHOULD NOT** mark sensitive parameters (passwords, API keys, tokens, PII) with `x-mcp-header`, as header values are visible to network intermediaries.»
- `server-tools.md:114-117` — «Clients using the Streamable HTTP transport **MUST** reject tool definitions where any `x-mcp-header` value violates these constraints. Rejection means the client **MUST** exclude the invalid tool from the result of `tools/list`.»
- `server-tools.md:111` — шесть MUST-ограничений на значение (непустое, синтаксис `1*tchar` по RFC 9110 §5.1, без CR/LF, регистронезависимая уникальность, только примитивные типы кроме `number`, только статически достижимые свойства).
- `server-tools.md:1052` — вывод корпуса: «`x-mcp-header` — вероятно, не нужен. … Пока — вносить не надо.»
- `changelog.md:843` — «сервер проксирует запросы в живой Avito API, и возможность клиента влиять на исходящие заголовки — это поверхность атаки. Рекомендация: **не включать** без явного разбора, какие заголовки допустимы.»
- `changelog.md:872` — механика «custom headers from tool parameters» (где объявляется, что разрешено, есть ли denylist) в прочитанных источниках не описана — то есть решения «включить» на текущем корпусе принять нельзя даже при желании.
- `server-tools.md:116` — клиенты на stdio **MAY** игнорировать аннотацию целиком, то есть для основного транспорта avito-mcp она не даёт ничего.

### Решение 6. DCR сохраняется как fallback; CIMD — в бэклог, с обязательным условием anti-SSRF

**Решение.** Существующий эндпоинт Dynamic Client Registration (`/register`) сохраняется и не удаляется в этом цикле. Client ID Metadata Documents (CIMD) выносятся в бэклог (M8.3). Условие допуска CIMD к реализации: **до** включения должна быть реализована и покрыта тестами защита от SSRF на загрузке metadata-документа. Без выполненного условия задача не берётся в работу.

**Обоснование.** DCR депрекирован, но не удалён, и changelog прямо оставляет его доступным для authorization server'ов, не поддерживающих CIMD; earliest removal — первая ревизия, выпущенная на/после **2027-07-28**. Поддержка CIMD имеет уровень **SHOULD**, а не MUST, а приоритетный порядок выбора механизма регистрации допускает откат на DCR. При этом CIMD по построению заставляет наш AS выполнять исходящий HTTP-запрос по URL, присланному **неаутентифицированным** клиентом (`/register` у нас открыт) — то есть добавляет новый класс уязвимостей в процесс, имеющий доступ к боевому Avito API.

**Источник.**

- `deprecated.md:550` (changelog) — «Deprecate the OAuth 2.0 Dynamic Client Registration Protocol (RFC7591) as a client registration mechanism in favor of Client ID Metadata Documents … **It remains available for backwards compatibility with authorization servers that do not support Client ID Metadata Documents.**»
- `deprecated.md:497` (реестр) — строка DCR: Deprecated in `2026-07-28`, Earliest removal — «First revision released on or after 2027-07-28».
- `spec-authorization.md:46` — «Authorization servers and MCP clients **SHOULD** support OAuth Client ID Metadata Documents.» (SHOULD, не MUST.)
- `spec-authorization.md:202-203` — приоритет: pre-registered → CIMD (если `client_id_metadata_document_supported`) → **DCR как fallback** (если есть `registration_endpoint`) → спросить пользователя.
- `authorization.md:533-534` — «Authorization servers fetching metadata documents **SHOULD** consider Server-Side Request Forgery (SSRF) risks…»
- `authorization.md:1454` — уже зафиксированное внутреннее ужесточение: «пункты 2 (SSRF), 3 и 4 списка ниже считать обязательной частью работы, несмотря на то что SSRF-защита в источнике имеет уровень **SHOULD**. Обоснование — avito-mcp ходит во внешнюю сеть из процесса, имеющего доступ к боевому Avito API».
- `governance.md:555` — конкретный минимальный набор мер, признаваемый достаточным: deny-list приватных и link-local диапазонов (`10/8`, `172.16/12`, `192.168/16`, `127/8`, `169.254/16`, `::1`, `fc00::/7`, `fe80::/10`) с проверкой **после** резолва DNS и защитой от DNS rebinding; только схема `https`; запрет или жёсткое ограничение редиректов с повторной проверкой адреса на каждом шаге; таймаут; лимит размера тела; требование `Content-Type: application/json`; отказ от проксирования тела ошибки наружу.
- `authorization.md:1102` — отдельно учтено, что готового чек-листа внутри спецификации 2026-07-28 больше нет: подсказки переехали в черновик `draft-ietf-oauth-client-id-metadata-document-00`, §6.4 и §6.8.

**Следствие для M2 (принято к сведению, решается в M2.4).** Весь Authorization-Server-слой, на котором держится `src/http/oauth/`, в `@modelcontextprotocol/server@2.0.0` отсутствует. Подробности и статус — риск Р10 ниже; настоящее решение лишь фиксирует, что «сохранить DCR» технически исполнимо в обоих рассматриваемых вариантах.

### Решение 7. Обёртка `structuredContent` `{status, http_status, items, count}` сохраняется как публичный контракт инструментов

**Решение.** Форма `structuredContent`, которую производит `toStructuredContent` в `src/core/tool-factory.ts`, не меняется. Ревизия снимает ограничение «только объект верхнего уровня», но мы этим послаблением **не пользуемся**. Меняется только комментарий в коде, который сейчас ссылается на снятое ограничение как на действующее требование протокола.

**Обоснование.** Обёртка появилась как обход ограничения 2025-11-25, но за время жизни перестала быть обходом и стала контрактом: она несёт `http_status` и `count`, на неё завязаны потребители и объявленные `outputSchema`. Снятие ограничения протоколом — это разрешение, а не предписание; менять публичную форму ответа 148 инструментов ради того, чтобы воспользоваться разрешением, — чистый риск без выгоды. Отдельно: требование соответствия `outputSchema` остаётся нормативным и жёстким, а значит любая правка формы сразу становится протокольным нарушением, а не косметикой.

**Источник.**

- `server-tools.md:1161` — «**Structured** content is returned as a JSON value in the `structuredContent` field of a result. This can be any JSON value (object, array, string, number, boolean, or null) that conforms to the tool's `outputSchema` if one is defined.»
- `server-tools.md:1225` (changelog, SEP-2106) — «Loosen `inputSchema` and `outputSchema` to allow any JSON Schema 2020-12 keywords, and `structuredContent` to allow any JSON value.»
- `server-tools.md:1031` — прямая рекомендация корпуса: «Рекомендация: **обёртку не убирать** (она несёт `http_status` и `count`, на неё завязаны потребители …), но комментарий обновить, чтобы он не вводил в заблуждение как «требование протокола».»
- `server-tools.md:1033` — «Servers MUST provide structured results that conform to this schema»; там же зафиксировано, что `additionalProperties` не встречается в `src/` ни разу, поэтому добавляемые `status`/`http_status`/`idempotent_replay` схемы не ломают.
- `server-tools.md:1169` — «`structuredContent` is server-produced result data and is unrelated to LLM "structured outputs"» — снимает соблазн переосмыслить поле.

**Следствия.** Задача M4.11 сводится к правке комментариев и добавлению теста, валидирующего фактический `structuredContent` каждого инструмента с объявленным `outputSchema` против этой схемы. Форма ответа при этом не меняется, и `schema_hash`/манифест по этой причине не пересчитываются.

### Решение 8. Депрекированные фичи не удаляются; долг фиксируется в реестре с датами

**Решение.** Ни одна депрекированная возможность (Roots, Sampling, Logging, DCR, HTTP+SSE, значения `includeContext: "thisServer"|"allServers"`) не удаляется из avito-mcp в рамках этой миграции. Вместо удаления заводится реестр долга (M8.4) с колонками «фича → deprecation SEP → ревизия → миграционный путь → earliest removal → наш статус». Параллельно действует гард (M0.4, закрыт в PR #44), запрещающий **наращивать** депрекированные поверхности.

**Обоснование.** Deprecated по политике жизненного цикла означает, что фича остаётся частью спецификации и полностью работоспособна; предписание адресовано новым внедрениям (**SHOULD NOT** внедрять), а существующим даётся окно не менее двенадцати месяцев, отсчитываемое от релиза ревизии. Фичи могут оставаться Deprecated без удаления существенно дольше минимального окна, то есть двенадцать месяцев — это пол, а не расписание. Удаление раньше срока не даёт ни соответствия, ни безопасности, зато ломает пользователей. Асимметрия «не наращивать, но и не удалять» — точное отражение политики.

**Источник.**

- `deprecated.md:9` — «фича **остаётся частью спецификации**, полностью работоспособна, но запланирована к удалению. Новые реализации **SHOULD NOT** её принимать, существующие **SHOULD** мигрировать до наступления „earliest removal“. При этом „earliest removal“ — это момент, когда фича становится _eligible_ к удалению, а не дата фактического удаления».
- `lifecycle-policy.md:98` — «Specify the **minimum deprecation window**: the number of months, at least twelve, that the feature must remain Deprecated before it is eligible for removal.»
- `lifecycle-policy.md:106` — «The minimum deprecation window is counted from that release.»
- `lifecycle-policy.md:179` — «Features may remain Deprecated, without removal, for much longer than the minimum deprecation window.»
- `deprecated.md:151-172` — реестр на 2026-07-28: шесть строк; Roots, Sampling, Logging (SEP-2577) и DCR (PR #2858) — с earliest removal «First revision released on or after 2027-07-28».
- `deprecated.md:216` — обязанность Tier 1 SDK помечать соответствующую поверхность `@deprecated` со ссылкой на deprecation-SEP и дату earliest removal.
- `deprecated.md:17` — отдельно зафиксировано и учтено: **удаление ≠ депрекация**. `logging/setLevel`, `ping` и `notifications/roots/list_changed` в этой ревизии именно **удалены** и в реестре Deprecated их нет; их отсутствие в modern-ветке — не долг, а требование.

**Подтверждение фактами (П1).** Обязанность SDK исполнена буквально и нас касается напрямую: `McpServer.sendLoggingMessage` в v2 помечен «@deprecated Deprecated as of protocol version 2026-07-28 (SEP-2577). **Remains functional during the deprecation window (at least twelve months).** Migrate to stderr logging (STDIO servers) or OpenTelemetry.» Это ровно то, что вызывает `src/logger.ts:182`. Значит наш код продолжит работать, а не сломается на апгрейде — что и обосновывает решение «фиксировать долг, а не удалять».

**Следствия.** В реестр долга обязаны попасть как минимум: Logging (`src/logger.ts`), DCR (`src/http/oauth/`), а также два **не**-депрекированных, но требующих переделки пункта — `resources/subscribe` (заменён на `subscriptions/listen`, `src/resources.ts:412-464`) и фоновое зеркало логов `bindMcpLogger(background: true)`, которое в modern-эре нарушает MUST NOT и потому подлежит не фиксации, а исправлению.

## Решения владельца проекта

Приняты владельцем и фиксируются здесь, чтобы не переобсуждаться:

**В1. Объём работ — весь путь M0…M7 до релиза 2.0.0.** Миграция ведётся до конца, а не до «достаточно хорошо». Отчёт предоставляется после каждого этапа M0…M7; переход к следующему этапу без отчёта по предыдущему не выполняется. Задачи этапа M8 («долг ревизии и опциональные возможности») в этот объём **не входят** и берутся отдельными решениями.

**В2. Исследовательский корпус не коммитится вообще.** `docs/mcp-2026-07-28/`, `MIGRATION_PLAN.md` и `MIGRATION_PROGRESS.md` остаются untracked и не попадают ни в один коммит. Защита — двухслойная, и оба слоя обязательны:

1. записи в `.gitignore` — чтобы файлы не попали в индекс случайно;
2. барьер на уровне упаковки пакета — исключение из tarball и из образа, плюс гейт в `test/release-hardening.test.ts`.

Второй слой обязателен независимо от первого, потому что `.gitignore` не влияет на `npm pack`: файлы попадали в тарбол по слишком широкой записи `docs/` в существовавшем allowlist `files` при отсутствующем `.npmignore` (см. П7). Проверяемый критерий — `npm pack --dry-run --ignore-scripts` даёт **127 файлов, ~480 kB, 2,7 MB** и ноль строк `docs/mcp-2026-07-28/`, при этом `docs/safety.md` в тарболе присутствует. **Статус: выполнено в PR #43 (M0.5).**

**В3. Канареечная проверка ограничивается read-инструментами; риск по write/money принят.** Обязательный read-набор: `meta_health`, `meta_capabilities`, `user_get_user_info_self`, `items_get_items_info`, `messenger_get_chats_v2`. Канарейка прогоняется при явно выставленном `AVITO_MCP_MODE=read_only` (либо флаге `--readonly`), и факт применения режима фиксируется в отчёте до начала прогона — дефолт режима `full_access` (П8), поэтому «по умолчанию безопасно» здесь не работает. Полный протокол и формулировка принятия риска — ADR 0002; **до подтверждения владельцем под ADR 0002 пункт В3 считается зафиксированным содержанием, но не подтверждённым формально** (см. Р9).

**В4. Изменения попадают в `main` только через PR, который мержит владелец.** Агент готовит ветку и pull request, но не мержит, не включает auto-merge, не создаёт теги и релизы и не публикует пакет. Решение о вливании в `main` и о выпуске релиза принимает владелец репозитория.

## Принятые риски и открытые вопросы

Не решения, а то, что должно быть на виду и адресовано в соответствующих задачах.

**Р1. Тихая регрессия идентичности вызывающего при переезде на v2 (P0). Адресуется в M1.2 и M2.2.** `callerPrincipal` (`src/core/pending-actions.ts:647-662`) читает `extra.authInfo?.clientId` и `extra.requestInfo?.headers?.authorization`. Под v2 эти поля всегда `undefined`: данные переехали в `ctx.http?.authInfo` и `ctx.http?.req?.headers`. Кодмод правку не делает: `handler` в `src/core/tool-factory.ts:310` — инициализатор переменной, а не колбэк `registerTool`, поэтому трансформ `context` его не якорит; `handler as any` в месте регистрации глушит тайпчек; `CallerExtra` — weak type, у которого с v2-шным `BaseContext` есть общее поле `sessionId`, поэтому присваивание легально. Итог: для всех 148 инструментов принципал **молча деградирует до `session:<id>`** — а это ровно тот идентификатор, который решает, кто вправе подтверждать отложенные money/public-действия и как считается rate limit подтверждений. **Ни tsc, ни существующие тесты, ни кодмод этого не видят** (тесты гоняют `InMemoryTransport` без `authInfo`, где обе версии дают `session:`). Требует ручной переработки `CallerExtra` под форму v2, перевода чтения заголовка на `Headers.get()` и интеграционного теста на реальный OAuth-принципал.

**Р2. Кодмод не видит `ImportTypeNode`. Адресуется в M2.7.** `rewriteDynamicImports` обрабатывает только `CallExpression` с `ImportKeyword`; конструкции `import('@modelcontextprotocol/sdk/shared/auth.js').OAuthClientInformationFull` в `test/oauth-provider.test.ts:38,206` остаются на v1-пути молча — без предупреждения и без маркера. Даёт 4 ошибки typecheck. Ручная правка.

**Р3. Коллизия имени `ctx`. Адресуется в M2.2.** Проект повсеместно использует собственную переменную `ctx: ToolContext`; кодмод хочет переименовать параметр `extra` → `ctx` и на единственной заякоренной площадке (`src/domains/meta.ts:433`) честно отказывается: «Cannot rename 'extra' to 'ctx': 'ctx' is already referenced in this scope. Manual migration required.» Ожидание из `sdk-typescript-4.md:823` («codemod сам перепишет `extra.*` → `ctx.*`») для avito-mcp не выполняется.

**Р4. Уточнение к `sdk-typescript-4.md:825`.** Документ советует перецелить `requireBearerAuth` на `@modelcontextprotocol/express`. Распаковка пакета показывает, что `requireBearerAuth`, `getOAuthProtectedResourceMetadataUrl`, `OAuthError`, `OAuthErrorCode`, `verifyBearerToken` экспортируются **прямо из корня `@modelcontextprotocol/server`**; это же подтверждает комментарий внутри кодмода. Новую зависимость на middleware-пакет добавлять не обязательно. Если перецеливание делается, в том же изменении обязательно менять бросаемые классы ошибок в `src/http/oauth/provider.ts` (4 места `InvalidTokenError`) на `OAuthError(OAuthErrorCode.InvalidToken)`, иначе протухший токен даст HTTP 500 вместо 401 — кодмод `instanceof` и бросаемые классы не переписывает.

**Р5. Обязательный прогон форматтера сразу после кодмода.** Кодмод не форматирует вывод: двойные кавычки вместо принятых одинарных, схлопнутые пустые строки, «лесенка» отступов внутри обёрнутых `z.object()`. Затронуто 30 файлов; без `prettier`/`eslint --fix` lint-гейт красный.

**Р6. Побочный эффект очевидной правки `inputSchema`. Адресуется в M2.9.** После `inputSchema: z.object(finalInputSchema)` падает `test/openapi-contract.test.ts:536` — тестовый дублёр `registerTool` делает `z.toJSONSchema(z.object(config.inputSchema ?? {}))` и получает двойную обёртку.

**Р7. Формулировка причины в критерии M0.5 — исправлена, риск закрыт.** Корпус попадал в пакет не «из-за отсутствия `files`-allowlist», а из-за слишком широкой записи `docs/` в **уже существовавшем** allowlist (П7). Лечение — сужение записи, а не введение нового механизма. Реализовано и закрыто в PR #43.

**Р8. Расхождение в счёте файлов, импортирующих SDK.** `sdk-typescript-6.md:928` говорит «минимум 14 файлов» — это только `src/`. Фактически SDK импортируют **31** файл (15 в `src/`, 14 в `test/`, 2 в `scripts/`). Влияет на оценку объёма M2, не на решения.

**Р9. Подтверждение владельца под протоколом канарейки (M0.6) — вне компетенции агента.** Пункт В3 фиксирует содержание решения; формальное подтверждение под `0002-canary-protocol.md` ставит владелец, и до этого момента задача M0.6 не считается закрытой полностью.

**Р10. В `@modelcontextprotocol/server@2.0.0` нет слоя Authorization Server (P0 для M2). Адресуется в M2.4.** Весь AS-слой, на котором держится `src/http/oauth/` (`OAuthServerProvider`, `AuthorizationParams`, `OAuthRegisteredClientsStore`, `mcpAuthRouter`, `redirectUriMatches`, классы ошибок), в v2-`server` **отсутствует** — grep по всем `.d.mts` в `server` + `core` даёт 0 совпадений. Он целиком переехал в замороженный `@modelcontextprotocol/server-legacy@2.0.0` (подэкспорт `/auth`) с описанием «Frozen v1 SSE transport and OAuth Authorization Server helpers … Deprecated; use StreamableHTTP and a dedicated OAuth server in production». В v2-`server` остался только Resource-Server-срез (`verifyBearerToken`, `requireBearerAuth`, `buildOAuthProtectedResourceMetadata`, `oauthMetadataResponse`). Выбор между «зависимостью на замороженный `server-legacy/auth`» и «выносом Authorization Server наружу» — продуктовое решение, которое настоящий ADR **не принимает**; дефолт плана — остаться на `server-legacy` как на переходном варианте. Отдельно учтено, что этот путь ведёт на депрекированный пакет, то есть создаёт долг, который обязан попасть в реестр M8.4.

**Р11. Modern-эра по stdio недостижима без `serveStdio(factory)`. Адресуется в M3.2.** Ручной `new StdioServerTransport()` + `server.connect()` навсегда остаётся legacy-эрой (поправка 2b решения 2). Риск здесь не технический, а интерпретационный: после механического переезда на v2 легко ошибочно счесть, что «сервер уже на 2026-07-28», хотя по stdio он всё ещё строго legacy. Проверяемый признак входа в modern-эру — не версия пакета, а фактическое использование `serveStdio(() => buildMcpServer(...))` и ответ `server/discover`, а не импорт какой-либо константы (поправка 2a).

---

## Что этот ADR не решает

- Выбор между `@modelcontextprotocol/server-legacy/auth` и выносом Authorization Server наружу (Р10) — продуктовое решение, задача M2.4.
- Судьбу собственного session-manager в `src/http/mcp-http.ts` при переходе на `createMcpHandler` — архитектурное решение, задачи M3.3 и M3.8.
- Переход в modern-only — M8.5.
- Разделение scope `avito:mcp` — M8.7.
