# ADR 0001 — Support MCP revision 2026-07-28 alongside legacy clients

Status: accepted
Date: 2026-08-01
Updated: 2026-09-07
Context: migration to the TypeScript SDK v2 and MCP revision 2026-07-28

[Architecture decisions](../README.md) · [Migration guide](../../MIGRATION.md) · [Conformance](../conformance.md)

## Decision

Serve MCP revisions `2025-11-25` and `2026-07-28` from one process. Keep `AVITO_MCP_PROTOCOL_ERA=legacy` as the default; `dual` accepts both revisions and `modern` accepts only the newer revision. Selecting a protocol revision is separate from upgrading the npm package.

The migration shipped in version 2.0.0. This record describes the decisions that remain relevant in 2.1.x. Current compatibility corrections are listed in the [changelog](../../CHANGELOG.md).

## Design choices

| Area                      | Decision                                                                         | Reason                                                                                                                   |
| ------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| SDK                       | Use the split `@modelcontextprotocol/*` v2 packages                              | The v1 server entry does not implement the new revision                                                                  |
| stdio                     | Use the SDK's `serveStdio` entry                                                 | It selects the connection's revision from the opening message; a plain legacy transport cannot serve the modern protocol |
| HTTP                      | Classify each request and dispatch to the selected revision                      | Legacy clients retain their handshake while modern requests are stateless                                                |
| Confirmation              | Keep `confirmation_id` and `meta_confirm_action`                                 | Durable explicit handles work across processes and protocol revisions                                                    |
| Multi round-trip requests | Do not use `inputRequired` for confirmations                                     | Approval remains an explicit tool operation with the existing policy checks                                              |
| Tasks extension           | Do not advertise `io.modelcontextprotocol/tasks`                                 | No implemented task lifecycle requires it                                                                                |
| Mirrored headers          | Do not use `x-mcp-header` on business arguments                                  | Tool inputs do not need to become HTTP headers                                                                           |
| Structured results        | Preserve the existing result wrappers                                            | Clients rely on `http_status`, array `items`/`count`, and replay markers                                                 |
| Client registration       | Keep bounded Dynamic Client Registration                                         | Client ID Metadata Documents need a separate SSRF-resistant fetch design                                                 |
| Deprecated features       | Preserve required compatibility; prevent new dependencies on deprecated surfaces | Removal is a separate compatibility decision, not an incidental SDK upgrade                                              |

The structured result wrapper is a project contract, not a protocol requirement. Object responses retain their upstream keys; only top-level arrays become `items` with `count`.

## Compatibility and validation

- Keep tool names, documented valid input schemas, resource URIs and safety defaults stable.
- Replay legacy behavior against the immutable 1.3.3 baseline. Document intentional correctness and security fixes instead of describing all responses as byte-identical.
- Validate modern discovery, envelopes, pagination, subscriptions, cancellation and OAuth behavior with the conformance suite.
- Test mutations and failure recovery against fixtures. A live canary uses only read tools; see [ADR 0002](0002-canary-protocol.md).
- Package public documentation and examples deliberately. Keep local credentials, research notes, work logs and conversation records outside Git, npm packages and container images.
